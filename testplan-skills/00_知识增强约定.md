# 写方案/计划之前 — 先对齐项目里的话

在 **分析、方案、计划** 动手写字前，如果公司里有需求库、Confluence、工单系统或向量检索，**建议先查一轮**，让写出来的测试方案和计划能对照到「哪条需求、哪份技术设计、哪次变更」，而不是纯靠模型猜。

**skills 包内 RAG（推荐）**：`testplan-skills/分析` Step B 执行：

```bash
python3 rag-engine/scripts/rag_prefetch.py 需求文档.md --out output/rag_context_plan.md
```

写方案/计划时 `@output/rag_context_plan.md`。详见 `rag-engine/SKILL.md`。

---

## 1. 为啥值得多说一句

- 简陋 PRD 往往缺边界，技术文档往往缺业务验收口径；两边对不上，方案和计划容易各说各话。  
- 方案和计划里有出处，评审、排期、拉开发联调都好说话。

---

## 2. 啥情况建议查

| 情况 | 咋办 |
|------|------|
| 用户只甩一句「出个测试方案」 | 先 `rag_prefetch` 或去外部库捞 PRD + 技术设计 |
| 有 **企微/Excel 项目任务表** | 读 sheet「项目任务」+ 里程碑行，见 `分析/references/enterprise_platform_inputs.md` |
| PRD 和技术文档版本不一致 | 对应迭代号或发布分支，列冲突清单 |
| 涉及钱、合规、对外权限 | 找法务/风控/接口 Owner 的书面口径 |
| 只有口头需求 | 列缺啥材料；可继续写但要标记「待确认」 |

如果用户已经贴了 **签字版 PRD + 定稿技术设计** 且没有歧义，可以不检索。

---

## 3. 实操四步（顺口就行）

1. **抠词**：模块名、PRD 编号、接口名、架构组件（Redis、MQ、缓存集群）、业务名词（秒杀、库存、订单）。  
2. **去哪搜**：PRD、技术设计、接口文档、评审纪要、线上缺陷复盘、旧方案和计划。  
3. **写摘要**：几条 bullet + 标注来源（PRD/技术/缺陷/纪要）；**别编页码**。  
4. **再走流水线**：分析 → 方案 → 计划。

---

## 4. 对各环节的顺手之处

| 环节 | 检索能多帮你啥 |
|------|------------------|
| 分析 | 业务规则、技术依赖、接口清单、历史故障 |
| 方案 | 测试策略依据、环境约束、风险热区 |
| 计划 | 发布时间线、人力窗口、里程碑对齐 |

---

## 5. PRD 与技术文档打架了

- 业务规则 PRD 说 A、技术文档说 B → 列冲突清单，拉产品 + 开发拍板。  
- PRD 缺验收标准、技术文档缺 SLA → 标 `T-xx（待澄清）`，方案和计划里占位，不编造数字。  
- 啥也没搜到 → 列缺啥材料；可以继续写但要标记「待确认」。

---

## 6. 脱敏

手机号、Token、真实合同金额、内网 IP 在传递和落库时都要处理，只留写方案和计划够用的信息。

---

## 7. 与 testcase-skills 的分工

| 本包（testplan-skills） | testcase-skills |
|-------------------------|-----------------|
| 测试方案 + 测试计划 | 测试用例 |
| 输入：简陋 PRD + 技术文档 | 输入：结构化需求 / 分析输出 |
| 产出：`*_testscheme.md`、`*_testplan.md` | 产出：`*_testcases.md` |

方案和计划评审通过后，可 `@testcase-skills/生成/SKILL.md` 进入用例编写。

---

## 8. 推荐前置：需求建模

需求还很粗、连 In/Out 都说不清时，先：

```text
@requirement-modeling/SKILL.md
@examples/prd_mini_seckill_auth.md
```

产出范围锚定后，再进入 **testplan-skills/分析**。  
演示 PRD：`examples/prd_mini_seckill_auth.md`；演示技术文档：`examples/tech_mini_seckill.md`。
