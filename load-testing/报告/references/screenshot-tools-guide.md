# 压测截图识别指南

从用户提供的截图中判断**工具类型**、**读出关键指标**、**标出应重点写的分析点**。分析时配合 `报告/SKILL.md` 工作流使用。

---

## 通用读图顺序

1. 确认工具与场景（界面特征、用户文字说明）
2. 读核心数字：样本量、平均 RT、P90/P95/P99、Throughput、Error%
3. 看曲线形态：RT 是否随并发爬升、TPS 是否有拐点、错误率是否突增
4. 若有资源图：CPU / 内存 / 磁盘 / 网络是否触顶
5. 把「图里看到的」写进报告，再推断瓶颈

---

## JMeter

**界面特征**：树形 Test Plan、Thread Group、监听器（View Results Tree、Summary Report、Aggregate Report）。

**聚合报告常见列**：

| 列名 | 含义 | 报告里怎么写 |
|------|------|------------|
| # Samples | 请求总数 | 样本是否足够（建议单场景 ≥ 1 万） |
| Average | 平均响应时间 | 与 P95 对比，平均好但 P95 差说明长尾严重 |
| Min / Max | 最小/最大 RT | Max 异常高要单独说明 |
| Error % | 错误率 | >1% 须在瓶颈章节展开 |
| Throughput | 吞吐（约 TPS） | 看是否随线程数不再增长 |
| 90/95/99% Line | 百分位 RT | **优先写 P95**，必要时补 P99 |

**曲线监听器**：Response Times Over Time、Active Threads Over Time — 用于判断 RT 与并发是否同步恶化。

---

## k6

**界面特征**：终端 summary 或 `handleSummary` 生成的 HTML 报告。

**常见输出**：

| 指标 | 含义 |
|------|------|
| `http_req_duration` (avg/p95/p99) | 请求耗时 |
| `http_reqs` / `iterations` | 请求量与迭代 |
| `http_req_failed` | 失败比例 |
| `vus` / `vus_max` | 虚拟用户数 |

**关注点**：`checks` 通过率、`http_req_waiting`（服务端等待）与总 RT 的关系。

---

## Locust

**界面特征**：Web UI 表格（RPS、Failures、Response times ms）、或命令行统计。

| 指标 | 含义 |
|------|------|
| RPS | 每秒请求数（类似 QPS） |
| Failures | 失败数与失败率 |
| Average / Median / 95%ile | 响应时间分布 |

---

## 云压测 / 自研平台

**常见元素**：并发数、RPS/QPS、RT 曲线、成功率、施压时长、地域/机型配置。

**读图要点**：

- RT 与 QPS 是否在同一时间段恶化
- 错误率上升是否与并发台阶一致
- 是否附带 CPU/内存/DB 监控（有则纳入分层分析）

---

## 资源监控截图

| 资源 | 警戒参考 | 瓶颈暗示 |
|------|----------|----------|
| CPU | 持续 > 80% | 计算密集、GC、线程过多 |
| 内存 | 持续爬升不回落 | 泄漏或大缓存 |
| 磁盘 IO | 利用率长期高位 | 慢盘、日志狂写 |
| 网络 | 带宽打满 | 包体过大、未压缩 |

**注意**：资源打满不一定是根因，可能是应用慢导致请求堆积；需结合 RT/TPS 曲线综合写。

---

## 报告书写提示

- 每张截图配 **一句话说明**（测的是什么、什么负载下）
- 用「图中可见…」「聚合报告显示…」等有据表述
- 无法从图里确认的指标写「未提供」，不要编造
