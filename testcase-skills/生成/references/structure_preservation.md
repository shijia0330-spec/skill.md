# 结构保持指南

> 对照文档示例：`seckill_finance_system/需求文档.md`、`功能需求文档.md`。

输出必须能与原始需求文档 **逐段对应**，评审和追溯时一眼能对上 PRD。

## 核心原则

### 1. 完全映射原始结构

- 原文有几级标题，输出保持几级（可在下层 **新增** 更深层级写检查点）
- 标题 **名称与顺序** 与原文一致
- 不合并、不拆分、不重命名原有章节

### 2. 只添加、不重组

- [OK] 在原章节下增加 `####` 检查点、列表项
- [FAIL] 把「2.2 商品管理」「2.3 秒杀功能」合并成「电商模块」等新结构

### 3. 术语一致

原文用「秒杀活动」「秒杀库存」「Redis 预热」「customer/admin」等，输出必须用相同术语。

### 4. 识别文档类型

| 类型 | 常见结构 |
|------|----------|
| 接口说明 | 模块 → 端点 → 参数/响应 |
| 业务流程 | 流程 → 阶段 → 检查点/操作 |
| 功能说明 | 模块 → 子功能 → 具体行为 |

## 正例（保持 PRD 结构）

**原文（节选）：**

```markdown
# 电商秒杀与财务一体化系统
## 2.1 用户认证与权限管理
### 2.1.1 用户注册
### 2.1.2 用户登录
## 2.2 商品管理
### 2.2.1 商品列表查询
```

**[OK] 正确输出：**

```markdown
# 电商秒杀与财务一体化系统 - 测试用例
## 2.1 用户认证与权限管理
### 2.1.1 用户注册
#### 重复用户名拒绝
- 已存在 username 再次 POST /api/auth/register
  - 预期：400，不重复入库
### 2.1.2 用户登录
#### 错误密码
- POST /api/auth/login 密码错误
  - 预期：401
## 2.2 商品管理
### 2.2.1 商品列表查询
#### 仅返回 active 商品
- GET /api/products
  - 预期：不含 inactive 商品 ID
```

**[FAIL] 错误：** 重组为「账号体系」「交易体系」等与原文无法一一映射的章节。

## 与测试用例编号

若项目使用 L-01、D-02 等编号，可在检查点标题或追溯表增加「对应需求：2.2.1 商品列表查询」，但 **不要** 改变 Markdown 标题层级与 PRD 的对应关系。
