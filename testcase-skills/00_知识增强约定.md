# 写用例之前 — 先能引用项目里的话

在 **规划、分析、生成** 动手写字前，如果公司里有需求库、Confluence、工单系统或向量检索，**建议先查一轮**，让写出来的东西能对照到「哪条需求、哪次变更」，而不是纯靠模型猜。

---

## 1. 为啥值得多说一句

- 减少和需求验收不一致导致的返工。  
- 用例里有出处，评审和复盘都好说话。

---

## 2. 啥情况建议查

| 情况 | 咋办 |
|------|------|
| 用户只说一句「把某某场景写全」 | 先构造检索词去库里捞 |
| 同一需求有好几个版本并行 | 对应迭代号或发布分支 |
| 涉及钱、合规、对外权限 | 找法务/风控/接口Owner的书面口径 |

如果用户已经贴了 **签字版验收表** 且没有歧义，可以不检索。

---

## 3. 实操四步（顺口就行）

1. **抠词**：模块名、PRD 编号、接口名、业务名词（比如预售占用、安全库存）。  
2. **去哪搜**：`rag-engine` 知识库（默认）；亦可叠加需求文档、评审纪要、线上缺陷复盘。  
3. **写摘要**：几条 bullet + 标注来源（需求/缺陷/纪要/RAG）；**别编页码**。  
   - 用例生成 Skill 已内置 Step 0a，执行：
     ```bash
     python3 testcase-skills/生成/scripts/rag_prefetch.py <需求.md> --out output/rag_context_<模块>.md
     ```
4. **再走流水线**：RAG → 规划 → 分析 → 生成。

---

## 4. 对各角色的顺手之处

| 环节 | 检索能多帮你啥 |
|------|------------------|
| 规划 | 发布时间线、旧风险、人力窗口 |
| 分析 | 业务规则、边界、接口依赖 |
| 生成 | 标签体系和大家写法一致 |

---

## 5. 搜不到或打架了

- 文档互相矛盾 → 列冲突清单，拉产品拍板。  
- 啥也没搜到 → 列缺啥材料；可以继续写但要标记「待确认」。

---

## 6. 脱敏

手机号、Token、真实合同金额在传递和落库时都要处理，只留测起来够用的信息。
