# 只有截图时 — 先把「想测啥」说明白（不写代码）

输入多半是 **页面截图**。输出是一份 **给人看的 Markdown**：页面上能点什么、建议怎么测。**这里不直接吐 Playwright 代码**，代码在后面执行阶段写。

用在：评审前快速对照、探索式测试随手记、和需求口头确认验收点。

> **有更好的方式：** 如果页面已部署（或本地 HTML），优先用 `00_DOM扫描.md` 提取真实 DOM 数据，比纯截图分析准确得多。截图分析仅用于没有 URL 访问权限的场景。

---

## 1. 建议怎么想（顺序随意一点也行）

**先看这是啥页面**  
登录、列表、表单、详情、工作台——不同类型关注点不一样（例如列表页常看筛选分页，表单页常看校验）。

**再列能动手的东西**  
按钮、输入框、下拉、链接——写清楚大概在哪一块区域，别只看颜色喊「蓝按钮」。

**再想几条路径**  
至少区分：**正常走完**、**故意填错被拒绝**；截图看不清的就写「待真机确认」。

**定位的事**  
这里可以提一嘴有没有明显的文案、testid 线索；**具体选择器**交给 `01_UI元素识别专家` 或 codegen。

---

## 2. 输出可以套这个壳（Markdown）

```markdown
# 截图页面 — 测试意图说明

## 页面干啥的
（一句话；假设已登录还是未登录）

## 能操作的控件
| 编号 | 大概长啥样 | 区域 | 点了会怎样 |

## 建议场景

### S1 — …
前置：……  
步骤：1… 2…  
期望：看得见……（尽量具体）

### S2 — …

## 看不清或要后台配合的
- …
```

---

## 3. 示例（秒杀财务系统 · `/seckill/admin`）

**S1 管理员创建秒杀活动**：登录 admin → 进入秒杀管理 → 填写活动名与时间窗 → 保存 → 期望列表出现新活动且状态为 UPCOMING 或 ACTIVE。

**S2 秒杀库存非法**：关联商品时秒杀库存填 -1 → 期望字段提示且不落库。

---

## 4. 写得好的几条标准

- 步骤里动词开头，对象能说清（按钮上的字、字段名）。  
- 期望写得出看得见的现象，少写「系统正常」。  
- 看不清的就承认，别硬编。
