# 页面可操作控件抽取（分析阶段）
---

## 1. 这一步到底产出啥

一线用起来就是一张清单：**页面上哪些东西值得自动化去点、去填**。输出给后面写 **pytest-playwright（Python）** 的同事或生成器用。

> **前置步骤：** 如果页面可访问（URL 或本地 HTML），先跑 `00_DOM扫描.md` 提取真实 DOM 数据。本文件描述的是 LLM 分析环节，DOM 扫描提供原始数据。

一般要收录：会改数据、会跳转、会弹出对话框的东西——提交、筛选、开关、上传都算。

一般不收：纯好看的图、只占位的图标条、纯排版容器、大段静态正文（除非里面有必须点的链接且场景单列）。

我们默认 **不靠一句话描述去蒙定位**（少数历史项目会用 MidScene 一类方案）；真要走到截图 / 视觉兜底，放在最后一档（文档里叫 Tier-3 / L3），并在 JSON 里写明「不得已」，方便评审砍成本。

---

## 2. 控件怎么分组（方便评审对照）

不用死记「按钮五大类」那种旧口诀，按**用户办事的路径**归类就行，评审时也这样说大家听得懂：

| 分组 | 典型控件 | 说明 |
|------|----------|------|
| 主导航与任务入口 | 顶栏菜单、侧栏、返回、面包屑中的可点项 | 关注路由与权限 |
| 数据提交 | 主按钮、保存、确认、下单、支付 | 常伴表单与校验 |
| 数据录入 | 文本框、选择器、日期、文件域 | 注意 label/placeholder/aria |
| 列表与表格操作 | 行内编辑、删除、批量操作、排序、筛选 | 注意行级 scope |
| 反馈与打断 | 对话框按钮、Toast 关闭、抽屉底部按钮 | 注意异步与遮挡 |

若页面混合多种分组，按「用户完成任务的最短路径」优先列出控件。

---

## 3. 定位三层（写入每条元素的 `locator_tiers`）

与全仓 **L1→L2→L3** 纪律一致，JSON 内统一使用键名 **`l1` / `l2` / `l3`**：

| 键 | 含义 | Playwright（Python）倾向 |
|----|------|---------------------------|
| `l1` | 稳定契约：`data-testid`、稳定 `id`、`name`、`aria-*`、`role`+可访问名 | `get_by_test_id`、`get_by_role`、`get_by_label`、`get_by_placeholder` |
| `l2` | 结构推断：祖先锚点 + 文案过滤 + 受控 CSS（远离哈希 class） | `locator(...).filter`、`get_by_text(..., exact=True)` |
| `l3` | 视觉兜底：截图区域与交互意图；禁止默认当主路径 | 项目自定义 vision helper；须 `fallback_only: true` |

另附 **`playwright_hints`**：字符串数组，每条建议是「可直接嵌进生成代码的片段级提示」，而非长篇散文。

---

## 4. 输出 JSON 契约（节选）

顶层字段建议保持稳定，便于 codegen 与静态检查：

```json
{
  "title": "页面业务标题或从产品文案推断",
  "description": "一句话说明页面职责与所属功能域",
  "elements": [
    {
      "id": "ctl_001",
      "name": "submit_order",
      "element_type": "button",
      "description": "收银条底部的确认下单按钮，附带回合计金额",
      "text_content": "确认下单",
      "locator_tiers": {
        "l1": "优先：data-testid=checkout-submit 或 role=button name=确认下单",
        "l2": "备用：结算卡片 footer 内最后一个 primary 按钮",
        "l3": "仅 DOM 不可用时：下半屏蓝色主按钮区域（高不确定性）"
      },
      "playwright_hints": [
        "page.get_by_test_id(\"checkout-submit\")",
        "page.get_by_role(\"button\", name=re.compile(r\"确认下单\"))"
      ],
      "fallback_only": false,
      "test_priority": "high",
      "confidence_score": 0.88
    }
  ]
}
```

字段可按平台扩展，但 **`locator_tiers` 三条线与 `playwright_hints` 不应省略**，否则下游只能瞎猜定位策略。

---

## 5. 交出去前自己看一眼

1. 别把纯文案当按钮报上去；吃不准就把 `confidence_score` 拉低，并在描述里写为啥（糊、挡、动态加载）。  
2. 和用户故事相关的控件往前排，评审省时间。  
3. `l1` 尽量写 testid、role、label 这类稳定线索，少用「左上角第三个」这种过后就找不着的话。  
4. JSON 键名跟你们工程约定走，别一组人用 camelCase 一组用 snake_case。

## 6. 与下游的衔接

- **规划 SKILL**：根据控件优先级排步骤与浏览器矩阵。  
- **执行模板**：将 `elements[].locator_tiers` 写入 pytest；参见 `执行/02_*`、`03_*`。  
- **自我修复**：定位失败时按 **L1（七种）→ L2 DOM → L3 视觉** 降级；运行期用 `执行/scripts/locator_healer.py`。详见 `执行/references/locator_strategy_web.md`。
