# 接口谁先谁后 — 依赖与执行顺序

手里已经有 `01` 整理出来的契约，这一步回答三件事：**哪些请求必须排在前面？哪些可以并行跑？哪里容易不稳定？**

---

## 1. 先分清两件事

- **自动化能串起来的依赖**：B 接口要的 id、token，是不是 A 接口返回的——这是测试脚本里要排的顺序。  
- **业务流程图上的审批、线下操作**：不一定都要自动化逐步演；能自动化的标出来，不能的别硬塞进脚本。

---

## 2. 常用几种依赖（团队内部叫法不一，大意如下）

| 标记 | 大白话 | 写脚本时注意 |
|------|--------|----------------|
| 登录 / 鉴权 | 没 token 统一 401 | 通常做成 fixture，注意过期时间和机器时钟 |
| 数据接力 | 先创建拿到 id，再拿 id 去查改删 | 中间可能要轮询或等待 |
| 强顺序业务 | 下单 → 支付 → 发货 这类不能乱序 | 别并行跑两条改同一单子的 case |
| 开关 / 多组织 | 同样 URL 不同组织/门店头（org-id）结果不同 | 前置里写清楚当前是哪个组织、开关开没开 |
| 最终一致 | 写完马上查可能还是旧数据 | 断言时要留一点延迟或重试策略，别写成秒级 flake |

一条接口上可以贴多个标签；排优先级时一般 **先把登录和数据接力理清**，再排业务顺序。

---

## 3. 建议输出长什么样（可按你们模板裁剪）

1. **依赖关系列表**：谁依赖谁、因为哪个字段、标记哪种类型。  
2. **分段执行**：每一段里哪些接口可以并行跑（例如批量只读）。  
3. **容易抖的点**：第三方超时、回调晚到、幂等重试——后面写断言别写死。  
4. **测试侧重点**：哪些适合契约级快照，哪些必须端到端走一遍。

---

## 4. 给模型的输入占位

`{api_digest}`：契约摘要；`{operations_index}`：接口索引。

要求可以包括：发现循环依赖就说哪里需要 mock；能并行的给例子；输出 JSON 或 Markdown 附录二选一，全文统一。

---

## 5. 有检索 / 知识库时

历史上同类接口出过什么事（超时、乱序），可以当旁证写进风险说明，**但不能推翻契约里已经写死的规则**。

---

## 6. 什么时候先别往下走

- 依赖关系绕成圈又没法 mock → 先把业务或架构说清楚。  
- 登录链没闭合 → 计划里必须先有拿 token 的步骤，别直接测业务接口。
