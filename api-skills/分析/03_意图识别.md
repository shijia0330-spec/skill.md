# 一句话诉求 — 测 UI、测接口还是测性能

从用户随便说的一段话里，判断出 **测哪一类**（页面 / HTTP / 性能），顺手把 URL、账号、性能指标等能抽的抽出来，交给后面编排。

---

## 1. 四类结果（`test_type`）

| 取值 | 什么时候选 |
|------|------------|
| `ui` | 明确要操作浏览器、看页面、跑前台路由 |
| `api` | 说的是接口、REST、Swagger、路径像 `/api/...` |
| `pt` | 明确谈并发、压测、TPS/RPS、P95/P99 这类 |
| `unknown` | 信息不够，硬猜会坑后面 |

---

## 2. 判断顺序（从上到下有一条命中就行）

1. 出现压测、并发、吞吐、P95 之类 → 倾向 **`pt`**。  
2. 出现网页、截图、界面、浏览器 → 倾向 **`ui`**。  
3. 出现接口、API、资源路径、Swagger → 倾向 **`api`**。  
4. 还对不上 → **`unknown`**，在 `reasoning` 里写缺啥（缺契约、缺环境、缺指标）。

---

## 3. 输出 JSON（给机器用）

占位：`{user_input}`；可选 `{rag_context}`（检索来的片段）。

字段保持稳定：`test_type`、`confidence`、`extracted_params`、`reasoning`。  
`extracted_params` 里常见键：`web_url`、`base_url`、`schema_url`、账号、`test_scenarios`、`performance_requirements`。

**规矩**：  
- `confidence` 别虚高；拿不准就低一点。  
- `reasoning` 写一句「为什么不是别的类型」。  
- 只输出 JSON，别夹 Markdown。

---

## 4. 各字段什么时候填

| 字段 | 备注 |
|------|------|
| `web_url` | 测页面且用户给了前台地址 |
| `base_url` | 直连后端时用 |
| `schema_url` | 能给 OpenAPI 地址就给 |
| `performance_requirements` | 性能场景填；不知道就 null |
| 账号密码 | 只有用户明确给沙箱账号时才写，别编 |

---

## 5. 跟后面的衔接

若 `confidence` 偏低（例如低于 0.65），下一步最好先问一句：**契约在哪、连哪个环境、性能要达到啥**，再批量生成脚本。
