# API 这条线：什么时候要先翻文档再动手

**版本**：2026-05  

和 `testcase-skills/00_知识增强约定.md` 是一类的：**手里先有项目里的说法，再生成东西**，少靠猜字段、猜版本。这边偏重 **接口文档、网关和环境**。

---

## 1. 为啥要单独说

写接口用例、依赖顺序、脚本断言之前，如果团队里有 Wiki、接口平台导出、或者向量检索能拉到**本项目**的说明，就先扫一眼。能减少常见翻车：字段名换了、某个版本标记废弃（deprecated，即文档里说「别再用这个字段」）、网关前缀加了一层你却还在调老地址。

---

## 2. 什么情况建议先检索

- 用户只说「帮我把某某接口用例补一下」，但没给 Swagger / OpenAPI 全文。  
- 同一套服务 **v1 和 v2 同时在跑**，或者不同门店/组织要在 Header 里带不同账套信息。  
- 涉及钱、登录鉴权、个人隐私、外部回调——以你们公司接口文档和风控要求为准，别按通用常识编。

---

## 3. 实际操作上四步

1. **想检索词**：路径片段（`/api/seckill`、`prepare-stock`）、`operationId`、业务词（「Redis 防超卖」「活动 ACTIVE」「限购」）。  
2. **去捞材料**：接口说明、变更记录（很多团队叫 Changelog）、重大技术决定（有的地方叫 ADR，就是「当时为什么这样设计」）、以前这类接口出过什么 Bug、有没有现成的 Postman / curl 示例。  
3. **写进后面的提示里**：标明这段话来自「接口文档 / 工单 / 缺陷」，**不要编第几页第几节**，没查证就别写。  
4. **再交给后面的文件**：按顺序一般是 `01_文档解析` → `02_接口分析` → `03_意图识别`，然后再到执行侧写用例或脚本。

---

## 4. 检索在各步能帮什么忙（直白版）

| 步骤 | 少检索时容易出的错 |
|------|---------------------|
| `01` 把文档整理成结构化信息 | 同一个中文名对应两个英文字段；文档里标了下线字段却没看见 |
| `02` 理清谁先谁后 | 漏了网关统一前缀、组织/门店 ID 放哪个头、功能开关（Feature Flag：灰度开不开） |
| `03` 判断用户到底要测啥 | 同一条 URL，在 A 产品是后台接口、在 B 产品是前端页面，容易搞混 |
| 执行侧写断言和造数 | 断言写到文档里已经不存在的业务码；测试数据不符合真实校验规则 |

没有检索能力就跳过这一步，**别堵死整条流水线**。

---

## 5. 两条纪律

- 文档和口头说法打架：**列出来让人拍板**，别自己替产品决定。  
- 库里什么都搜不到：**明说缺什么材料**，别假装读过文档。
