# 把接口说明收成一张「机器好读」的清单

分析流程的第一步：**Swagger / Postman / 内部 Wiki** 乱七八糟进来，这里统一收成一份结构化结果（通常是 JSON），后面的依赖分析、写用例都靠它。

如果团队有检索（Wiki、向量库），先把材料找齐，做法见 **`00_知识增强约定.md`**，再跑本篇。

---

## 1. 常见输入长什么样

| 来源 | 实操时注意 |
|------|------------|
| OpenAPI 3 / Swagger 2 | 看清楚 **servers**，有时开发、测试、生产三套地址都在文档里 |
| Postman 导出 | collection 里的变量名要捋顺，别留着「{{host}}」不改 |
| PDF、Wiki、扫描件 | 可能有 OCR 错字；拿不准的字段标出来，别硬编 |
| 注册中心导出的 JSON | 有时会多一坨治理字段（负责人、SLO 等），可以单独放进扩展字段，别丢 |

---

## 2. 收进来至少要覆盖哪些块

键名可以和你们工程约定略有出入，但**意思**要对上：

- **服务基本信息**：标题、版本、说明、**根地址**（文档里的 servers / baseUrl）。  
- **鉴权**：Bearer、Cookie、API Key、OAuth 等怎么配；哪些接口要、哪些不要。  
- **每个接口**：路径 + 方法；路径参数、Query、Body、返回各状态码大概长什么样。  
- **字段规则**：必填否、类型、长度、枚举、示例；文档里说「别用了」的字段（deprecated）要标出来。  
- **质量备注**：解析哪里拿不准，列个待核对清单，比瞎填强。

---

## 3. 交给模型整理时可以用的提示骨架

占位：`{file_name}`、`{doc_format}`、`{document_content}`

大意如下（可按你们平台改口吻）：

> 下面是一份接口说明，请整理成**一份合法 JSON**，不要包 Markdown。  
> 文件名：{file_name}；类型：{doc_format}；正文：……  
> 要求：顶层分块清晰；每个接口要有 method/path；密钥和真实手机号用占位符；两处定义打架时写在 conflicts 里。

## 4. 落地前人工扫一眼（几分钟能救命）

1. 文档里出现的接口，JSON 里是不是都有？  
2. 日期、金额这类字段，类型是不是跟线上真实返回一致？  
3. 写了要登录的接口，security 有没有对上？  
4. 标了废弃的字段，后面写用例的人知不知道别再去断言默认值？
