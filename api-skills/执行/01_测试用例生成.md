# API 用例怎么铺 — 别只会 Happy Path

前置：`01` 契约、`02` 依赖顺序心里有数；若有 `03` 意图结论和规划里的范围更好。

---

## 1. 分层怎么想（不必死板凑「五类」）

现场更常用的是 **按风险叠覆盖**，下面代号只是方便对应评审：

| 代号 | 干什么 | 举例 |
|------|--------|------|
| H | 主路径成功 | 创建成功、查询能对上 |
| E | 契约边界 | 最长最短、枚举之外、小数精度 |
| X | 协议或业务拒绝 | 401、422、业务错误码 |
| P | 粗看一眼耗时 | 单次耗时量级（不是专业压测报告） |
| S | 低成本安全 sanity | 匿名访问、过期 token、明显越权试一下 |

**底线**：对外真正会打的接口，至少 **H + X**；钱相关的多加 **S**。

---

## 2. 一条用例建议写清什么

- **编号**：稳定，后面脚本、报告、缺陷都引用同一个。  
- **调哪个接口**：和契约里的 operation 对得上。  
- **前置**：登录、造数、开关（Feature Flag：灰度）——写清楚。若一整条流程必须严格顺序执行（注册成功后才拿得到 id），设计时明确「第几步依赖第几步」；落到脚本时可用声明式 **`scenarios`**（见 **`02_测试脚本生成.md`** 第 6 节），不必拆成多个互不传递变量的独立 case 硬凑。  
- **请求怎么造**：合法 JSON，别嵌 JS/Python 表达式。  
- **期望**：状态码 + 关键字段；负例要写清期望的错误形态。  
- **收尾**：要不要删数据、要不要退款，避免脏库。

---

## 3. 给模型下任务时的占位

`{api_digest}`、`{operations_index}`、`{dependency_edges}`、`{execution_stages}`

大意：按 H/E/X/P/S 产出 `cases[]`，请求体必须是合法 JSON 字面量；依赖前置响应的地方在 setup 里说明白；产出 JSON，附带 `notes` 和 `open_questions`。

## 4. 写完自检（十分钟）

- 负例的期望和业务文档还对不对？  
- 引用上游返回字段的地方，上游步骤有没有写？  
- 断言是不是松到「只要 200 就行」？
