# API 自动化跑完 — 留下能扯皮的证据

约定的是：**脚本放哪、报告至少要有啥、失败了往哪分流**。具体用 Jenkins 还是 GitLab CI 不管，字段一致就行。

---

## 1. 产物放哪

| 东西 | 建议 |
|------|------|
| 用例脚本 | `tests/api/` 或你们生成器约定目录，固定入口方便 CI |
| 环境说明 | `.env.example` 列出 `BASE_URL`、token 作用域等 |
| 契约快照（可选） | 若做契约测试，golden 文件单独目录 |

---

## 2. 追溯用的编号

- **用例 ID**：例如 `TC-API-001`，pytest 里用 marker 或注释挂上。  
- **构建信息**：能带上 Git 提交号或 CI 构建号最好，查历史省心。

---

## 3. 报告最少要能回答

「哪条用例、调的哪个接口、过没过、挂了的话请求响应长什么样（脱敏后）。」

形式任选：Allure、JUnit XML、pytest-html、JSON 都行，**但要有一份机器能扫的**，方便门禁和看板。

---

## 4. 命令行大概长这样

```bash
pytest tests/api -q --maxfail=1 --alluredir=allure-results
```

跑完把通过数、失败数、报告路径、失败用例列表回给编排或群里。

---

## 5. 红灯怎么办

| 情况 | 倾向 |
|------|------|
| 契约变了脚本跟不上 | 走 **`api-skills/自我修复`** |
| 明显服务端 bug | **`bug-reporter`**，附 curl 或请求摘录 |
| 环境 itself 挂了 | 标 skip/xfail，挂工单，别硬算失败 |

**pytest 失败时**：引擎根 `conftest.py` 会自动在 **`output/bugs/`** 写缺陷**草稿**（`BUG-*.md` + `bug_list.md`）。先按草稿里的「分流」判断，再决定自愈还是定稿报缺陷。关闭：`DEFECT_DRAFTS=0`。

---
